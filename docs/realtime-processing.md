# Processing and extension work

The managed `RemotePluginInstance::process()` and `LocalPluginInstance::process()` paths do not acquire application locks, including try-locks or sleeping/spinning locks. They do not allocate or reclaim C++ request storage. This covers core MIDI merging, AAPXS filtering/handoff, parameter value caching, GUI output publication, standard parameter/preset notifications and `request_process`.

Android Binder processing still uses its existing synchronous transaction. Binder scheduling, framework internals, tracing and plugin/host-supplied code are outside this application-level guarantee. Arbitrary plugin DSP and a host's custom extension callback must observe their own processing constraints. This change does not provide realtime priority inheritance through Binder.

## Handoffs

Instances allocate their queues and start an extension worker during AAPXS setup, before processing. A queue has 64 records and one consumer. Producers make at most four atomic reservation attempts; the consumer never waits for an unpublished record. Atomic operations used by processing are checked as always lock-free at compile time, including double parameter values on all four Android targets.

MIDI producers copy complete UMP sequences into queues. Processing merges records that fit the destination's current payload capacity, leaving excess records queued for later blocks. A record larger than the port's entire payload capacity is discarded. Partial UMP records are rejected. The ordinary input/output/GUI record capacity is the instance's configured event MIDI buffer size (8 KiB by default).

Processing validates and filters complete AAPXS SysEx8 messages, copying their existing wire bytes into a separate preallocated inbox. The worker parses those copies, invokes extension handlers, copies replies into owned request buffers and completes callbacks. Processing can immediately reuse its port buffer. Reply delivery, cancellation, pending tables, Binder channels and typed completion ownership continue using their existing synchronization on non-processing threads.

The inbox accepts records up to twice the existing 1 KiB AAPXS parser capacity plus the MIDI header, enough for its encoded UMP packets. A full inbox drops the wire message; an outstanding request then reaches the existing timeout/error path. Outgoing request handoff rejection immediately reports an error and releases its session/table registration. There is no inline Binder or callback fallback on processing threads. `RealtimeByteQueue::rejectedCount()` exposes queue rejection counts for native diagnostics.

Standard parameter/preset notifications use a coalescing atomic mask; `request_process` uses a coalescing flag. They do not compete for inbox capacity. Other payload-free host notifications use a bounded queue with copied URIs; excess notifications are dropped and counted. Notifications do not promise one IPC transaction per original invocation.

The worker blocks on a nonblocking eventfd notification (Linux/Android), with no fixed-period polling. Producers publish work before signaling; an atomic flag coalesces wakeups. The worker consumes the event and clears the flag before dispatching work, so arrivals during dispatch leave a wakeup for its next wait. An idle worker sleeps indefinitely. Request registration/cancellation wakes it to recompute the earliest deadline; its blocking descriptor wait expires at that deadline even when audio has stopped. Instantiation/readiness transitions also signal retained early layout requests. Shutdown signals the descriptor before joining. The single-descriptor wait uses `ppoll`, with a monotonic deadline recomputed after interruptions.

Processing may issue a nonblocking notification write after work publication. It still acquires no application locks and performs no C++ allocation, but kernel synchronization/scheduling and interrupted-syscall retries are outside a bounded realtime guarantee. Descriptors are created before processing and stay alive until the worker has joined and all producers have stopped. The macOS native harness uses a nonblocking pipe for the same wait/notify protocol.

Replies and notifications still have worker scheduling latency; a SysEx8 reply is normally returned in a later audio block. A blocked user callback blocks its extension worker, rather than processing; it can eventually cause handoff backpressure.

Remote parameter-layout notifications start an asynchronous scan with one outstanding request. RT-unsafe metadata getters retain their Binder route. SysEx8 requests are enabled only when the peer acknowledges the corrected parser. With an unacknowledged legacy plugin, the worker issues at most one Binder request per completed audio block, across extensions, and requires a later block after transmission before sending another. This drains the redundant MIDI replies that older services enqueue for Binder calls. Inactive instances need no audio progress. A stopped-audio request expires on the worker deadline, and cancellation removes queued transmissions before aborting their channels. A blocking legacy query from this worker is refused rather than waiting for itself to dispatch it. Reply callbacks only copy their result and wake the worker; a complete scan publishes the replacement, while errors/timeouts preserve the previous layout.

An arriving layout notification supersedes a scan already in progress. The worker waits only for its outstanding read to finish, then restarts at the count instead of reading the obsolete tail or publishing a partially stale result. Repeated notifications coalesce without adding abandoned requests behind a held read. No transport callback or request storage is freed early. A scan observes supersession between read steps and before publication; legacy pacing/draining still applies to its replacement. Frequent changes can postpone publication until a complete current scan finishes.

Optional transport negotiation uses an extra shared-memory descriptor through the existing `addExtension` mapping operation, plus a reverse-direction FD for each nonempty extension. It sends no unknown extension opcode and adds no URIDs. Both upgraded peers acknowledge before plugin construction/first host callback, then use independent plugin/host payload buffers. Original URIs advertise their former logical capacity, even though the FD contains reserved extra bytes; only an opted-in service maps those extra bytes. This prevents older state handlers from treating the prefix as additional payload space. Logical capacities, POD payloads, C structs, AIDL and SysEx8 bytes remain unchanged. An old peer leaves the descriptor unacknowledged: both directions retain the former offset-zero payload view. Simultaneous bidirectional traffic against an old binary can still collide; separation requires both peers to upgrade. A missing or undersized reverse mapping disables separation.

## Control exclusion

Control calls serialize off the processing thread. The control thread publishes suspension and blocks on a separate eventfd notification until previously entered DSP blocks leave. The last leaving block signals only while a control thread is waiting; there is no periodic control wait. Processing announces activity and checks suspension using lock-free atomics. A suspended/inactive local block clears its outputs instead of calling DSP or waiting. Complete AAPXS requests are still copied to the worker inbox. During active control suspension, queued UI MIDI is merged and ordinary MIDI is copied into a preallocated FIFO per input port before shared input lengths are cleared. DSP replays retained events in order before newer input. Late clock/delta timestamps are removed; fresh input retains its timestamps. A partial drain retains complete packets for the next block. Deactivation requests a processing-side reset so retained notes cannot leak into a later activation.

Each input FIFO is allocated in prepare while processing is stopped, using four actual port payloads up to 256 KiB, plus bounded channel/note history. Overflow discards the backlog and schedules pedal release, channel mode messages and explicit MIDI1/MIDI2 note-offs for previously delivered notes, on their original groups/channels, before later notes are delivered. Recovery can span multiple blocks and repeated overflow cannot restart it indefinitely. Overflow is observable through the internal retention counter. This is bounded recovery, not lossless storage for an unlimited control suspension. One caller owns each instance's processing and port FIFOs, as for its shared audio buffers.

All worker/Binder plugin extension handlers run between DSP blocks. `is_command_rt_safe` continues selecting the existing SysEx8 transport at the initiator, but does not authorize concurrent access to plugin state. Parameter scans, local preset JNI controls and activation/deactivation use the same exclusion. “RT-safe” alone does not imply thread-safe concurrent access. Control operations can produce silent blocks, especially long state/preset operations.

## SDK and lifetime

General typed AAPXS queries remain non-realtime APIs. In an annotated processing scope, synchronous wrappers return their existing default value or `RT caller` error, and async wrappers return `-1` without accepting a request or invoking its callback. Payload-free host notifications use their separate handoff. Callers must not construct allocating callback captures or invoke other non-realtime APIs inside DSP just because a defensive refusal exists. `RealtimeScope` is implemented in the core library, so SDK consumers in other shared objects use the same annotation even with hidden symbol visibility. Its bounded atomic thread registry avoids cold TLS initialization and allocations. It supports 256 distinct annotated threads at once; exhaustion temporarily refuses general SDK queries on every thread until capacity returns.

Host and native plugin proxies are constructed before processing and retrieved from instance caches. Metadata/index snapshots stay immutable and alive until instance destruction. Atomic value cells are shared by stable ID across revisions, preserving changes made through an older snapshot during publication. Processing never takes layout/publication locks or a global sidecar lookup lock.

Teardown stops and joins the worker before releasing sessions, dispatchers and buffers. `PluginHost::destroyInstance()` called from a worker callback defers deletion to a lifecycle thread, allowing the current handler to return before the join. Plugin release runs while its host facade and extension contexts still exist. The host must stop making processing calls before destroying an instance; direct deletion from inside its own worker callback is not supported.

Native C++ API/ABI changes require affected SDK consumers within the same app to rebuild. Peer-facing C extension/AAPXS structs, AIDL, opcodes and POD payload formats are unchanged. Logical capacities are preserved. Upgraded peers negotiate optional extra memory mappings; existing counterparts retain the former serialization layout.

Incoming plugin-side SysEx8 requests now have owned contexts, URIs and payload storage on the extension worker. An extension that completes after its handler returns must call `aap::xs::retainAAPXSReply(request)` from `aap/core/aapxs/recipient-aapxs.h` during dispatch. Keep the returned shared handle, write its `request().serialization` payload/data size, and call `complete()` on a non-processing thread. The completion uses the original SysEx8 route; it does not depend on thread-local state, instance activity or a borrowed recipient pointer. Immediate `send_aapxs_reply()` calls continue to work with the original context. Borrowed Binder requests cannot be deferred with this API.

The recipient store allows at most 255 live unanswered requests. Releasing an abandoned handle releases its buffer and permits another dispatch; rejected incoming requests reach the initiator's existing timeout. `complete()` publishes once, returns false on queue backpressure/invalid payload/cancellation, and allows backpressure retries with the same retained handle. Reply encoding has independent scratch storage and publication uses the existing bounded output queue. No completion runs on processing. Teardown detaches the sender and waits for any active publication before releasing its queue target. Retained handles remain safe to access or complete after teardown, with completion returning false; they do not extend the lifetime of plugin state. Extensions must separately stop work that uses plugin objects before those objects are destroyed.

Negotiated directional blocks also carry request/reply lengths in their reserved prefix when both peers acknowledge the length capability. Binder recipients publish the actual serialization data size before completion; initiators validate it and copy just those bytes into each request buffer. Short/empty replies retain their real size, and out-of-capacity replies fail without copying. The prefix never changes an extension's POD record. Peers without length support keep the former capacity-limited copy.

Typed clients reuse completed request objects and payload buffers in a per-client pool, bounded by eight idle entries and 2 MiB of idle buffer capacity. Concurrent requests keep independent storage. Reentrant completion cannot recycle a buffer while its initiating send still borrows it. Detached pending requests retain the pool until their transport callback safely reclaims them. This reduces repeated buffer/object allocations; callback closures, waiter objects and transport bookkeeping can still allocate off processing. Payload-free host notifications use their existing channel too, so their length metadata cannot race a host query on the same direction.

The parameter and preset extension implementations publish their own atomic count snapshots through the generic lifecycle contract. Their handlers return the same serialized four-byte replies without reading mutable plugin state per poll. These extensions declare other metadata getters read-only and identify their own change notifications; the dispatcher has no built-in count caches or metadata-read whitelist. Other extensions can independently declare the same policies and own different state. Unsafe plugin-state access still uses control exclusion, and control work can still suspend DSP.

Service dispatch uses extension-declared request flags. Without annotations, plugin requests use control exclusion and invalidate extension snapshots afterward. An extension may declare a read-only handler, or a handler that accesses only its own immutable/atomic state and can run concurrently without DSP suspension. RT-safe transport selection remains separate. The runtime never identifies parameter/preset functions or supplies their replies.

Each extension owns its recipient context, cached replies and state-change hook. Generic setup/prepare and potentially-mutating requests invoke registered hooks under control exclusion. Host notifications declare their invalidation and coalescing policy; the runtime coalesces payload-free opcodes -1..-32 independently per extension URID and retains them until lifecycle readiness. Extension-specific local notification effects run in that extension's outgoing-request hook. Contexts detach before destruction and are released exactly once after plugin release. Standard parameter/preset implementations use these same hooks; no standard URI/opcode or handler-identity test remains in local dispatch.

These optional hooks extend the in-process AAPXS definition ABI. All affected native consumers within an app must rebuild. Request records, extension payloads, opcodes, shared capacities and peer negotiation stay unchanged; older plugin/host counterparts remain supported over their existing serialization.

## Validation

Run `tests/native/run-aapxs-lifecycle.sh` and `python3 tests/native/check-aapxs-wire-compatibility.py 9e17764f`.

The native suite runs debug/release UBSan regressions, including idle workers without polling, concurrent wakeups racing with sleep, shutdown wakeups, deadline rearming/cancellation without audio, concurrent queues, saturation/reuse, copied legacy wire messages, cancellation before delayed delivery, parameter snapshot publication, actual local/remote processing, blocked worker completion, incoming control exclusion and worker-triggered teardown. The processing fixture traps on mutex/try-lock use and C++ allocation/reclamation; deliberate failing probes verify those guards. macOS uses an injected test-only dyld lock interposer to include libc++ mutex calls. Android UI/JNI and memory setup are substituted in the host fixture; processing, dispatch, transport, cache and queue implementations are production code.

The event-driven worker and DSP/control primitive fixtures also run directly as standalone arm64 native executables in debug/release on the connected Pixel and Samsung devices, using the real eventfd backend. These tests do not install or exercise plugin APKs. The native Android core and JS controller builds are checked for arm64-v8a, armeabi-v7a, x86 and x86_64. These checks do not replace audio/device stress testing or mixed-version APK testing. No Gradle test assets or `build.gradle.kts` changes are required.
