# Service binding regressions

Run `./tests/hosting/run-bindings.py` from the repository root. Requires Python 3, a JDK with JNI headers, a C compiler, and cached Kotlin compiler/runtime, reflection, and coroutines jars matching `gradle/libs.versions.toml`. The runner uses those existing dependencies directly and cleans temporary binaries. It does not edit Gradle configuration, package Android native assets, install an APK, or require a device.

The tests compile the actual `AudioPluginServiceConnector.kt` and `PluginServiceConnection.kt`. Android service/Binder behavior and AAP native registration are controlled doubles; a tiny host JNI stub handles the native connected notification. These are connector lifecycle tests, not Android Binder integration tests or confirmation of the Samsung MARs report.

The first patch covers null/disconnected/dead bindings, false/throwing platform binds, connector closure, synchronous callback delivery before `bindService` returns, late callbacks during retries, registration failures, reentrant listener invalidation/closure, and concurrent terminal events. Completion and platform unbinding are claimed once per attempt; stale attempts cannot clean up a new attempt.

The second patch adds coroutine cancellation, cleanup when cancellation happens during registration, and a real 10-second missing-callback deadline followed by a successful retry. The timeout uses the existing `AudioPluginException`; external coroutine cancellation remains cancellation. It bounds waiting for a callback, but cannot preempt synchronous Android/JNI calls that are already executing.

The third patch makes binding independent of the Android main thread. The platform double models `LoadedApk`: a bind with no executor gets its callbacks on one shared main thread, so going back to that fails these tests. They cover waiting for a bind on the main thread, a blocked callback holding up nothing else (including a bind nested in it), overlapping callbacks of one connection, a failing listener, and two real waits past the deadline. Callbacks run on any pool thread and no order is promised; a feature that needs one keeps its own queue. A bind completes before its consumers run, so their work is not subject to the deadline. Once registered, a connection belongs to the connector: cancelling the bind only ends that caller's wait.

For API verification, run `./tests/hosting/run-bindings.py --api-baseline 3b4f8239`. This compares public Kotlin metadata (including nullability, default arguments, and suspend functions) and public JVM descriptors for the connector, its existing Connection class, and its companion. Only compiler-generated accessors for private implementation are excluded. No production C/C++ headers, JNI/AIDL signatures, or public Kotlin declarations change.

[Android's binding documentation](https://developer.android.com/reference/android/content/Context#bindService(android.content.Intent,%20android.content.ServiceConnection,%20int)) specifies releasing the platform connection even when binding returns false. [Kotlin's cancellable continuation documentation](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/suspend-cancellable-coroutine.html) describes cancellation racing callback delivery; the tests exercise cleanup in that interval.
